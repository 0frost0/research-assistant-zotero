# 科研助手与 Zotero 接入可行性调研

日期：2026-09-21。性质：技术调研与建议。用户随后认可“小型 Zotero 插件 + 现有后端”主线，并提出分类知识库、纳入阅读笔记和优先云端保存；这不等于已经批准迁移真实资料或配置云盘账号。

## 1. 结论

可行，而且建议把主线转向“Zotero 阅读与资料管理 + 轻量科研助手插件 + 现有 Python 后端”。

重点不是把当前网页完整搬进 Zotero，而是把阅读、选区翻译和引用管理交给已有工具，把开发投入放在有来源的问答、多文献比较、研究计划和可审阅的科研记忆。

不把“先生成整篇中文 PDF”设为入库、问答或研究流程的前置条件。原文可直接成为检索证据，中文回答是生成层任务；跨语言检索质量仍须用实际问题验收。

保留现有阅读器、译文、原件和笔记作为旧数据入口，不在本轮删除、覆盖或强行迁移。

## 3. “复用翻译插件”可以解决什么

### 3.1 推荐复用：阅读中的翻译

Translate for Zotero 的文档明确支持选区翻译、批注翻译、笔记中的译文，以及多种翻译服务。它可以作为日常阅读工具，与科研助手并列工作。[S5]

第一版不调用其内部私有函数、不读取其密钥，也不解析其界面 DOM。用户照常使用翻译插件；科研插件读取 Zotero 的原文选区或标准批注，再交给科研后端。

自动翻译可能把译文放入批注评论或正文，插件还允许修改原文相关字段。科研助手必须区分原文、用户评论、机器译文和 AI 分析，不能把“批注里出现的中文”自动视为论文原文。[S5]

### 3.2 不能保证解决：整篇双语 PDF

Zotero PDF2zh 项目明确使用 PDF2zh / PDF2zh Next，且仍需要独立翻译服务。我们当前全文翻译同样使用 PDF2zh Next，因此更换入口并不自动消除模型超时、输出截断、漏译和排版问题。[S7]

其 README 在本次读取时还保留了 2026-08-19 的全面重构通知。这不是断言它不可用，而是说明不宜立即把科研助手的核心工作流强依赖于它的内部实现。

建议把全文翻译定位为外部可选能力。用户已有译文可以保留为同一条目下的衍生附件，但不能默认与原文逐句对齐，也不能用机器译文替代原文证据。

## 4. 官方接口是否足够

| 能力 | 核验到的接口或机制 | 对本项目的意义 |
| --- | --- | --- |
| 读取条目、集合、附件与笔记 | 本地 API / Web API v3 | 可以建立受控文献同步，不必读取原始 SQLite 文件 |
| 读取当前选择、修改本地条目 | 插件内 JavaScript API | 适合本机 Zotero 9 的插件路径 |
| 选区弹出菜单、阅读器事件 | Zotero.Reader.registerEventListener | 添加“解释选区”“加入研究笔记”等操作 |
| 条目与阅读器侧栏 | Zotero.ItemPaneManager.registerSection | 显示来源、任务状态和结果 |
| 笔记写回 | JavaScript API 的事务与 saveTx | 用户确认后新建附属笔记，不覆盖旧笔记 |
| 带来源笔记 | Zotero 原生批注转笔记、页面回跳 | 可以复用来源定位体验 |

依据官方开发文档与阅读器文档。[S1][S3][S4]

版本限制很重要：本地 HTTP 写入能力被官方文档标为 Zotero 10+，需要运行时用户授权；本机是 9.0.6，不能把这些接口当成已经可用。Zotero 10 还改变了本地版本号含义，需要按实例标识分区，不能与云端版本混用。[S2]

本地 API 的附件入口可返回指向本机文件的重定向，而非远程服务器可直接读取的 PDF。现有 Python 后端在 agent-assistant，不能拿到一个 Windows 路径就完成解析；需要本机插件读取用户选定的附件并上传授权的副本。[S2]

## 5. 三条路线比较

| 路线 | 好处 | 代价与限制 | 建议 |
| --- | --- | --- | --- |
| 现有网页 + 本地 API 桥接 | 最少改界面，适合验证文献导入 | Zotero 9 的写回受限；当前选区交互不自然；跨机器需本机桥接 | 可作为只读技术验证 |
| 小型 Zotero 插件 + 现有后端 | 选区、批注、笔记在阅读现场完成；保留 Python/GPU 服务 | 要维护版本兼容、来源映射与可靠通信 | 推荐作为产品主线 |
| 把整套助手重写成 Zotero 内部插件 | 表面上只剩一个应用 | Python 解析、GPU、向量库、后台任务都要重新组织 | 不建议 |

这是一项架构判断，不是实测工期承诺。第一版不追求全库双向同步或替代 Zotero 阅读器。

## 6. 推荐的职责边界

```text
Windows：Zotero 9
  原文 PDF / 文献条目 / 批注 / 用户笔记
  Translate for Zotero：日常选区翻译
  新科研插件：明确选择、发送请求、展示结果、确认写回
          |
          | 现有 SSH 隧道上的受控请求
          v
agent-assistant：现有 Python 科研后端
  授权附件副本 -> MinerU / 已有解析缓存 -> 检索与证据
  单篇问答 / 多篇比较 / 研究计划 / 审批 / 执行记录
```

职责建议：

- Zotero 是书目信息、原附件与人工批注的主入口；插件不接管其同步实现。
- 后端保存已授权附件的哈希快照、解析缓存和研究产物，不反向替换 Zotero 原件。
- Zotero 中的 AI 笔记是用户确认后的交付结果；后端仍保留模型、来源与修订记录。
- 翻译插件提供阅读便利，但其内部数据结构和接口不成为我们的核心依赖。
- 不把 23119 端口转发到服务器或公网。官方明确说明本地 API 读取不要求认证。[S2]
- 后端连接需要应用级身份校验、受控文件大小和幂等请求，不仅依靠“只在本机显示”。

## 8. 最小原型与验收

建议先在独立测试配置与合成资料上验证，不先动真实文献库：

1. 用户在 Zotero 选一篇 PDF，点击“发送到科研助手”，后端显示任务并返回稳定映射。
2. 在原文选一个短句或批注，点击“解释”，结果带原附件和来源位置。
3. 确认后保存为该文献的新附属笔记；再次提交同一个结果不产生重复笔记。
4. 从结果回到 Zotero 原文页；没有精确坐标时诚实标为页级定位。
5. 再扩展到两篇文献比较；资料范围严格等于用户明确选择的文献。

验收不能只看“按钮能点”：

- 重复发送不重复上传、不重复建索引或调用模型。
- 同名文件、同一 PDF 对应多个书目条目、附件更新和缺失文件均有明确处理。
- 隧道中断后恢复任务状态，不盲目重放付费请求。
- 未确认的 AI 草稿不进入已确认科研记忆，原文与翻译严格区分。
- 用户取消外发或写回时，没有相关文献内容离开本机或覆盖既有笔记。
- 和已装 Translate for Zotero 共存，真实鼠标选区与批注流程正常。
- 禁用新插件后，Zotero 原有阅读、翻译和资料仍能使用；后端旧笔记仍可访问。

第一阶段暂不做全库双向同步、自动修改书目、自动翻译整篇、自动修改原批注或把译文坐标映射成原文事实。

## 11. 分类知识库与云端保存：用户需求补充

### 已确认的方向与待确认的默认值

用户认可小型 Zotero 插件与现有后端的主线，希望按照 Zotero 的文件划分建立不同知识库、包含对应阅读笔记，并优先保存于云端，例如坚果云。

以下是建议设计，尚未实现：把“文件划分”理解为左侧分类集合及子分类，不是物理磁盘目录；由用户选择哪些集合启用知识库，默认包含子分类但提供开关与范围预览。不自动扫描或上传整个文献库。

### 分类与知识库规则

- 一个选定集合绑定一个稳定 knowledge_base_id，记录来源库与 collectionKey；改分类名只更新显示名，不新建库。
- 同一条目能属于多个集合，这是 Zotero 的既有语义。后端用多对多成员关系表达，不为每个分类重复复制和解析同一内容。[S8]
- 一个分类新增或移除文献，更新知识库成员关系；移出分类不等于删除 Zotero 原件或其他知识库共享的数据。
- 父分类是否包含子分类由库设置控制；多个集合组合成一个专题库可放到第二阶段。
- 删除分类时先将对应知识库标为归档/来源失联，保留历史研究结果，不自动清理原文或备份。
- 查询默认为当前知识库，可显式多选库做比较；没有成员的库返回空结果，不能退回全库搜索。

### 阅读笔记是一类独立证据

知识库内容建议分为原文证据、原文批注、用户阅读笔记、知识库专属笔记、已确认的 AI 总结。原文引用显示附件与页码，个人笔记显示作者来源、笔记修订及关联文献，两者不混用。

文献级笔记默认随该文献进入其所属知识库；只希望用于某个研究方向的笔记显式绑定该知识库。独立 Zotero 笔记按所属集合或用户选择纳入，而不是丢弃没有 PDF 父项的笔记。

未确认 AI 草稿不作为已确认记忆召回；Zotero 导入笔记可能混有机器生成内容，保留外部来源，不自动宣称全是人工撰写或已经核验。

查询可选择“仅文献 / 仅笔记 / 文献与笔记”。共享笔记修改时，各库引用最新有效修订，但历史回答保留当时的证据快照。

### 推荐的云端分工

| 数据 | 推荐的工作位置 | 同步或备份 |
| --- | --- | --- |
| Zotero 条目、集合、原生笔记 | Zotero 本地数据与官方数据同步 | 保留其既有同步机制，不用网盘文件覆盖数据库 |
| Zotero PDF 等附件 | Zotero 管理的附件与按需本地副本 | 可使用已有坚果云插件或 WebDAV；个人库路径需实际验证 |
| 助手知识库定义、成员、笔记镜像、任务与来源记录 | 现有 agent-assistant 服务器 | 导出带版本的可恢复文件包到坚果云独立目录 |
| 解析结果、向量检索索引 | 现有服务器上的服务存储 | 解析文件可归档；数据库用一致备份，Qdrant 用正式快照 |
| Windows 助手端 | 插件设置及有限缓存 | 不要求保存完整解析库、向量库或模型副本 |

这是“远端运行 + 云盘归档”方案，不是声称坚果云的文件同步接口能代替向量检索服务。现有 agent-assistant 已在另一台机器，第一版不需要为了“不在个人电脑保存知识库”再迁移模型或新增一套计算部署。

Zotero 官方明确区分数据同步和附件同步：条目、笔记等由 Zotero 服务器同步，WebDAV 用于个人库附件，不支持群组库附件。[S9] 坚果云官方提供 Zotero 的 WebDAV 配置及官方插件，但这不等于原生 Zotero 笔记会作为独立 Markdown 文件自动同步到坚果云。[S10]

因此，如果用户希望“笔记也能在坚果云中看到”，需要科研助手额外导出 UTF-8 Markdown/JSON 及来源索引；第一版建议由服务器单向导出。直接在网盘编辑这些导出文件后自动写回 Zotero，不属于第一阶段，避免并发覆盖。

### 备份必须能够恢复

建议在助手自己的云盘目录保存知识库清单、成员映射、笔记版本、所需附件/解析文件清单与哈希，以及数据库和索引快照。不要手工更改 Zotero WebDAV 管理的附件目录。

运行中的 Zotero 数据目录不能直接放进云盘同步目录，官方明确提示数据库损坏风险。[S11] 助手的活动数据库和 Qdrant 数据目录也不采用同步文件夹作为运行盘：先生成一致备份/官方快照，再上传归档。[S12]

知识库元数据、笔记和向量快照要关联同一个备份代次；必要时短暂暂停写入。未完整上传并校验的代次不标记成功。不保存 API 密钥，不默认承诺多设备、多写入端可以直接编辑同一备份。

换电脑时，插件连接远端服务即可继续使用；服务器故障时应能用云端归档恢复，或凭原件、笔记和配置重建索引。后者是否需要已有模型和兼容环境必须在恢复清单中写明。

“云端优先”不等于 Zotero 桌面端完全零本地数据：其本地元数据和正在阅读的附件/缓存仍存在；若要求连这些都不落本机，需要另行评估浏览器或远程桌面路线。[S9]

### 当前代码接入风险与第一阶段验收

当前索引支持 sources 筛选，但没有知识库成员与权限模型。特别是 [全局同步清理](D:/workspace/research_assistant/research_assistant/retrieval/unified_index.py:265) 会把本次 sources 以外的已索引内容停用和清除，不能直接对每个分类依次调用现有全局 sync，否则可能影响其他知识库。这是静态代码推导的接入风险，不是已发生的数据丢失。

第一阶段应先建立持久化的库定义、文献/笔记成员关系和增量同步边界，再复用解析与检索。库范围必须由后端检查并传递到文献、笔记和图像取证路径；不能先全库检索后只在前端隐藏其他库。

建议先用两个合成分类、一篇跨分类共享文献、一篇独有文献和若干不同来源笔记验证：

1. 分类创建知识库、包含子分类的开关、重命名保持身份。
2. 共享文献只解析一次；移出一个库不损坏另一个库。
3. 文献与笔记联合检索来源清楚、范围不串库、空库不搜全库。
4. 文件或笔记修改只更新相应内容；网络中断不会误判成员全部删除。
5. 模拟云盘目录导出版本化归档，并在隔离目录完整恢复；真实坚果云上传需单独配置及授权。

本轮仅记录需求与方案，没有创建知识库、配置坚果云、读取云盘凭据、上传真实文献、调用模型或修改正在运行的业务服务。
