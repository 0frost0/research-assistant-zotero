## 使用与设计

插件知识库勾选范围 → 输入问题 → **依据原文回答** → 查看结论及逐字引文 → 返回 Zotero 原页。普通“检索”保持不调用生成模型。

问答在 Zotero 中通过 `ask-async` 提交本地持久化任务，再轮询 `jobs/{job_id}`；结果写入独立的 `qa_jobs.sqlite3`。服务重启会把 queued/running 标记为 interrupted，不会自动重发模型请求；最近 200 个任务保留用于查看状态和结果。原有同步 `ask` 接口仍保留给兼容客户端。

历史中的失败/中断任务可以由用户明确点击“手动重试”，服务最多允许同一任务链 3 次重试；重试创建新任务并保留 `retry_of`，不会覆盖旧失败记录，也不会后台自动重试。成功、排队或执行中的任务不能重复提交。

问答执行中可以点击“停止问答”。服务先把 queued/running 任务原子写成 `cancelled`，再取消本进程协程；异步收尾不会覆盖这个终态。历史显示“用户已停止”，不自动重试；已经发出的模型请求可能仍由供应商计费。

同一 Zotero 工作台会为问答生成一个临时会话标识。连续追问包含“它/这篇/该方法”等指代时，服务只读取同一知识库范围内最近 3 个已完成任务的**问题和已核验结论文字**，用于补足检索词和回答上下文；历史记录不作为证据，当前问题仍必须重新检索并引用当前 PDF。普通独立问题不改变检索词，切换知识库后不会混入旧会话内容。

工作台提供“新会话”按钮。用户换主题或怀疑上下文不再相关时可以主动清除追问上下文；它只更换会话标识，不删除论文、笔记或问答历史。

`knowledge/qa.py` 复用既有检索上下文补全；从最多 20 个候选中选 6 条、合计不超过 12000 字符。去掉同一原文页内已完整包含的摘录，不用相似度去重否定句或不同研究的相反结论。

生成原子结论 → 本地核验引文 ID/原文摘录 → AI 先判断证据是否覆盖问题范围，再仅基于该条实际引文做支持性核对；有缺口时至多一次纠正，可改写补检索，再生成并核对。最多 2 次检索、4 次模型调用，单次模型等待 45 秒，总等待 180 秒，无 SDK 自动重试。相同查询直接复用已有证据；纠正时传入上一轮失败原因。查询改写由回答/复核结构中的字段提出，不额外调用模型。失败保留候选原文；未核验草稿不显示成答案。

AI 复核是支持性检查，不是科学事实认证。第一版只回答原文事实，笔记仍走原来的独立搜索；不将个人观点混入原文。回答结束前重查知识库 revision，期间变更则丢弃旧回答。

用量来自真实模型返回。失败或未返回 usage 的调用单独标为未知，不按零费用解释。`qa_runs` 仅存运行统计，不存问题、论文摘录和密钥；原有 SQLite 数据保持。

每次问答结果的 `trace.calls` 记录调用角色（answer/review/rewrite）、终态、耗时、用量是否已知和错误类型；不记录调用 payload。这样可以区分检索成功但模型超时、结构化输出失败、支持性复核拒绝和用户主动停止，便于生产排障与费用核对。

最短复跑流程：先用 `benchmarks/export_qa_feedback_candidates.py --db <qa_jobs.sqlite3> --scope original --output candidates.json` 只导出论文原文候选；复制 `benchmarks/qa_feedback_review.example.json`，填入候选 ID 和人工核对结果；再运行 `benchmarks/approve_qa_feedback_candidates.py --candidates candidates.json --review review.json --root <项目根> --output qa-development.json --split development`。脚本会在当前知识库中核对 PDF、页码和摘录，失败时不会替换输出文件。个人记录候选继续使用 `--scope notes`，不进入论文事实 QA。

也可以从自己的 Zotero 知识库批量生成待核对问题模板，整个过程不调用生成模型：

```powershell
python benchmarks/create_qa_review_template.py --root . `
  --questions questions.json --output qa-review-template.json --backend multimodal
```

`questions.json` 只需包含 `id`、`query` 和 `kb_ids`。输出中的 `candidate_evidence` 只是当前检索建议，`expected`、`no_answer` 和 `human_decision` 为空；研究者在 Zotero 中核对页码和逐字摘录后，再删除候选字段并运行现有 validator。脚本默认拒绝覆盖已有输出，避免把旧评测集静默替换。

也可以直接从问答历史提取去重后的真实问题，减少重复录入：

```powershell
python benchmarks/create_qa_review_template.py --root . `
  --qa-jobs .data/zotero/qa_jobs.sqlite3 --scope original `
  --output qa-review-from-history.json
```

该入口只读取已完成任务中的问题和知识库 ID，不读取模型回答作为标准答案；它仍会重新检索当前证据，并要求人工确认后才能进入 development/test 数据集。带有 `incorrect`、`partial` 或 `correct_no_answer` 反馈的问题会优先进入队列；个人记录问题不允许进入这个原文 QA 模板，应使用个人记忆模板。输出文件包含论文摘录，默认使用私有权限保存。

## 真实调用发现的缺陷

- GLM-5.3 是强制思考模型（[官方说明](https://docs.bigmodel.cn/cn/guide/capabilities/thinking-mode)），初版 20 秒过短。更重要的是 `model_copy(request_timeout=...)` 不会更新已建立的 SDK HTTP 客户端：已改为在创建客户端之前传入 45 秒，新增测试锁定此行为。超时请求的供应商消费可能仍发生，未知 usage 单列，不自动重试。
- 首次成功回答附带了试验终点和排除条件，但引文只覆盖人数；复核看到完整上下文而误放行。已改为原子结论及“仅实际摘录”复核，并将失败原因送入唯一一次纠正。
- 评测曾将服务失败时无输出算入“无错误回答”，口径已收紧：超时/不可用不参与拒答正确性统计，单列完成率。历史 `glm-live-final.json` 的 fixed 无答案指标应作废，该次实际为超时。
- GLM-5.3 复核多次达到输出上限，换 JSON 模式也未解决。最终保持 GLM-5.3 回答，用同一服务的 GLM-4.7 非思考复核；最后一题成功回答 200 人，实际摘录完全支持该结论，2 次调用合计 1512 token、39.4 秒。单题成功不等于稳定性或速度提升。截断异常能取得 completion.usage 时也计入用量。

本轮全部真实调试共 16 次模型调用，累计已知 **14021 token**，另 **4 次未取得用量**（包含超时及旧版 SDK 截断异常）；不能将已知数当作账单总消耗，也不推算人民币费用。后续不再为同一检查重复调用。
