# Zotero 有据问答：当前交付说明

> **阅读目标**：先看清楚系统解决什么问题，再看它如何工作、代码在哪里、测试证明了什么。历史迭代和论文方法对照不放在主流程里。
>
> **当前分阶段验收**：先完成 Qwen Embedding + Reranker，再做维度覆盖，最后做完整性判断。第一步的同池实验、改善和退步见 [Qwen 第一步验收](Qwen第一步验收.md)；下文实验门禁是已有能力记录，不表示后续阶段已验收。
>
> **2026-11-13 第三阶段**：已按用户确认优先复用官方RINSE，作者仓库的74,841条特征级数值复现通过；官方包不含完整原文reader／checkpoint，尚不能对新文献打分。固定版本、产物缺口和验证记录见 [RINSE第三阶段](RINSE第三阶段.md)。
>
> **后续资源纠偏**：不索要私有权重、不自建训练数据；已确认S2G-Judge真实LoRA及3,000/300条公开数据，但许可仍未明确。MuSiQue-Full公开原文与充分性标签可下载，官方CC BY 4.0，完整dev字节／结构核验通过。Qwen3-8B 的 evidence-chain-audit 在 held-out 上复现相对收益：balanced accuracy 61.72%→73.05%，充分召回 38.28%→50.78%，不足误放行 14.84%→4.69%；但绝对召回仍不足，未接入生产。reserve 上更严格的格式提示未通过相对收益条件，保留原 chain 作为研究候选。Zotero 现有 52 题仅完成锚点覆盖边界审计，尚无独立充分性 gold。见 [充分性公开资源调研](充分性公开资源调研.md)。
>
> **reserve 后续探索**：balanced、逐槽位 checklist、精确关系 guard 均未满足改善目标；第三／四组已补同片原 chain 对照并完整校验。原 chain 仍为研究候选，停止本轮提示措辞探索；实际误放行与含无效输出的不足类失败率分别报告。详见上述公开资源记录。
>
> **证据证书机制实验**：第五组32对已完整回收；生成证据链＋原文引句匹配＋同模型新会话核验，召回从同片chain的46.88%降至21.88%，不足类失败率未改善，故不采用。引句忠实性和核验误拒是主要损失来源，详见公开资源记录。
>
> **SURE-RAG 资源复核**：论文源包只有 TeX／图片／样式，没有可直接运行的官方代码、权重或 HotpotQA-RAG v3 数据下载入口；`mnc13/PROClaim` 是另一套 PubMed/COVID 争议 claim 核验仓库，不能误认成 SURE-RAG 实现。论文指标不作为本项目结果，详见 [充分性公开资源调研](充分性公开资源调研.md)。
>
> **当前版本**：源码 / Zotero 插件 `0.3.11`。本地 XPI：`output/zotero/research-assistant-0.3.11.xpi`。2026-11-18 收尾新增复核／笔记范围决策的严格布尔校验与 claim index 类型检查；本轮 GitHub 归档授权与生产服务部署分开，历史真实验收不冒充本版重新验收。
>
> **一句话结论**：Zotero 中已经形成“限定文献范围 → 检索证据 → 生成带引文的原子结论 → 本地核验 → 模型支持性复核 → 返回原文页”的工程闭环；生成前充分性门禁和图文问答是实验能力，已完成流程安全验收，但尚无独立真实论文质量指标。

## 1. 要解决的问题

### 1.1 日常科研中的具体问题

用户在 Zotero 中问一个问题时，系统不能只返回“看起来合理”的摘要，而要回答：

- 这个结论来自哪篇论文、哪一页、哪一段原文？
- 引文是否真的支持这条结论，而不是只与主题相关？
- 证据不足时，系统是否会拒答，而不是用常识补全？
- 文献、个人阅读笔记和 AI 草稿是否被清楚区分？
- 文献或图片在问答期间发生变化时，旧结果是否会被丢弃？

### 1.2 本交付明确不解决的问题

当前版本**没有**声称：

- 在真实科研论文测试集上提高了准确率或拒答率；
- 复现了 SetR 或 RINSE 的训练模型；
- 已完成多模态精排或图表识别质量评测；
- AI 的“充分”判断是概率置信度或科学事实认证；
- 已发布插件、已部署生产服务或已替换用户正式 Zotero profile。

这些边界不是附带说明，而是本项目的验收口径。

## 2. 当前产品行为

### 2.1 默认的原文问答流程

默认请求不启用实验开关，流程如下：

```text
Zotero 选择知识库
        ↓
原文检索：BM25 + Qwen 向量 → RRF 合并
        ↓
默认 adaptive：Qwen3-Reranker-0.6B 精排（不可用时降级）
        ↓
去重、限制最多 6 条 / 12000 字符
        ↓
回答模型生成原子结论 + evidence_id + 逐字引文
        ↓
本地检查 evidence_id 和 quote 是否匹配当前 PDF
        ↓
支持性复核：只检查实际被引用的引文
        ↓
显示结论、引文、页码和 Zotero 跳转
```

普通“检索”不调用回答模型。只有点击问答后才生成答案。

### 2.2 证据不足时的默认处理

- 生成的引文无法在当前证据中核对：删除该结论。
- 复核认为证据只与主题相关、不能回答问题：清空结论并保留缺口。
- 资料不足但可以提出更准确的检索词：adaptive 最多补一次检索或轮换尚未使用的候选。
- 仍不足、模型超时、结构化输出失败或知识库版本变化：不展示未经核验的答案。

默认原文问答最多 4 次模型调用，具体包括回答、复核以及至多一轮纠正；没有 SDK 自动重试。

### 2.3 个人笔记不是论文证据

“仅笔记”和“文献与笔记”使用独立路径：

- 论文原文只进入原文 QA；
- Zotero 批注、专题笔记和用户记录只进入个人记忆 QA；
- 两类结果分区显示，不能合成一条无来源结论；
- 未确认 AI 草稿和归档记录不进入默认个人记录检索；
- 笔记编辑使用 revision，引用旧版本时不会静默替换成新版本。

## 3. 实验能力 A：生成前证据充分性门禁

### 3.1 它解决什么问题

普通回答流程是在生成之后发现“引文不支持”。充分性门禁把一个更早的问题单独拿出来：

> **在调用回答模型之前，当前选中的证据集合是否已经覆盖了用户问题真正要求的对象、条件、比较双方、指标和单位？**

它的目标是减少“先生成、再发现证据不够”的无据回答，不是给答案打一个可信度分数。

### 3.2 实际流程

```text
检索并选择候选证据
        ↓
充分性模型只返回结构化判断
        ├─ sufficient=true  → 回答 → 本地引文核验 → 支持性复核
        └─ sufficient=false
              ↓
        adaptive：最多一次补检索或候选轮换
              ↓
        再判断一次
        ├─ sufficient=true  → 回答 → 核验 → 复核
        └─ sufficient=false → 不生成答案，显示证据缺口
```

门禁模型不能使用历史回答或常识补事实，只能引用当前输入的 evidence ID。判断结果必须满足：

- `sufficient` 是严格布尔值；
- `evidence_ids` 必须来自当前证据，不能重复；
- `sufficient=true` 时必须有支持证据且不能同时声明缺口；
- `sufficient=false` 时必须明确写出缺口。

### 3.3 调用和失败边界

- 默认关闭，不改变原有文字问答行为；
- 仅原文问答可用，仅笔记请求会拒绝该选项；
- adaptive 最多两次门禁判断；
- 门禁开启后原文最多 4 次模型调用：门禁、门禁、回答、复核；
- 门禁失败、超时、输出非法、证据版本变化时失败安全，不回退到无门禁生成；
- 首版是**未经校准的模型判断**，不是 RINSE 的三信号判别器，也没有独立人工 gold。

| 责任 | 代码 |
|---|---|
| 结构化 schema 和严格校验 | `research_assistant/knowledge/qa.py`：`Sufficiency`、`validate_sufficiency` |

## 4. 实验能力 B：图文证据问答

### 4.1 它解决什么问题

论文中的图表事实不一定出现在文字图注中。图文模式允许回答模型读取受控图片，但必须把以下三类信息分开：

1. **原文引文**：来自 PDF 文字，必须逐字核对；
2. **图像观察**：来自模型读取像素，标记为 `citation_type=visual` 和 `observation_source=model_derived`；
3. **图注或 OCR**：只能作为上下文，不能冒充模型对像素的观察。

### 4.2 安全流程

```text
召回同源 / 同页 / 同版本图像证据
        ↓
再次验证知识库范围、来源、页码、版本、hash 和预算
        ↓
生成阶段发送受控 data URL
        ↓
视觉回答使用 visual citation
        ↓
支持性复核再次读取实际引用图片
        ↓
结果只保存 provenance 和 hash，不保存 data URL
```

图片预算为每轮最多 2 张；单张和总 data URL 大小、像素数、长边均有限制。图片能力必须在服务配置中显式声明为 `supports_images=true`。

### 4.3 已完成的真实端点验收

当前连接 `go/glm-5.3-flash` 已通过有界合成图片探针。之后进行了真实 GLM 与原生 Zotero 10.0.8 的隔离联合验收：

- 真实调用：回答 1 次、复核 1 次，共 2 次；
- 输入 2190、输出 121 token，未知用量 0；
- 合成图与 PDF 来源一致；
- 原生窗口成功解码图片；
- 视觉观察未伪装成逐字引文；
- 历史重开成功；
- 持久化结果不包含 data URL。

这证明“端点、API、插件、图片 provenance”已连通，**不证明真实论文图表识别质量**。

| 责任 | 代码 |
|---|---|
| 图像候选分组和版本安全 | `research_assistant/knowledge/visual_evidence.py`、`retrieval/evidence_groups.py` |
| 图片编码和受控读取 | `research_assistant/knowledge/service.py` |
| 视觉回答与复核 payload | `research_assistant/knowledge/qa.py` |
| 视觉 API | `research_assistant/web/knowledge_api.py` |
| Zotero 图片展示和 visual 标签 | `deployment/zotero/assistant.js` |
| 有界真实调用账本 | `benchmarks/visual_fixture.py`、`check_visual_readiness.py` |

## 5. 工程实现总览

### 5.1 服务端分层

```text
Zotero 插件
  └─ bridge.js / assistant.js
       └─ Bearer API：knowledge_api.py
            ├─ KnowledgeService：知识库和检索
            ├─ EvidenceQA：原文证据问答
            ├─ MemoryQA：个人记录问答
            ├─ CombinedQA：两条路径分开编排
            └─ QAJobStore：异步任务、历史、重试、取消
```

### 5.2 为什么使用异步任务

Zotero 不应因为模型请求阻塞界面。`ask-async` 创建本地持久化任务，插件轮询任务状态：

- 任务结果可以从历史重新打开，不重复调用模型；
- 服务重启时 queued/running 标记为 interrupted，不自动重发；
- 用户可明确取消或手动重试；
- 最近 200 个任务保留；
- 统计遥测不保存问题、论文摘录、密钥或图片 data URL。

### 5.3 当前默认检索算法

默认 adaptive 原文检索采用：

1. BM25 和 Qwen 向量分别召回；
2. 用 RRF 合并，不直接相加不同量纲分数；
3. 使用 Qwen3-Reranker-0.6B 精排候选；
4. 去除同页内被完整包含的摘录；
5. 最多发送 6 条、12000 字符给回答模型。

精排不可用时保留召回结果并显示降级状态。`hybrid_set` 的互补集合选择只保留为实验开关，因为开发用例中出现过丢失标准证据锚点的失败。

算法细节、论文借鉴边界和检索消融放在：[检索筛选算法升级.md](检索筛选算法升级.md)。

### 6.2 门禁专项测试覆盖

`tests/test_evidence_sufficiency.py` 覆盖：

- 充分判断发生在回答之前；
- 不足时最多一次补检索；
- 两次不足不调用回答模型；
- fixed 策略不额外补检索；
- 候选轮换不重复搜索；
- 非法 evidence ID、重复 ID、缺口不一致时拒绝；
- 门禁超时与模型失败不伪装成 no evidence；
- 文献 revision 变化时停止；
- 图片 hash 变化时停止；
- 门禁、回答、复核使用同一图片身份，但遥测不保存图片内容；
- CombinedQA 不把门禁传给个人笔记路径。

### 6.3 原生复跑

使用全新输出目录，不触碰正式 Zotero profile：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File benchmarks/run_zotero_native_fixture.ps1 `
  -Target output/zotero/native-sufficiency-<new-name> `
  -VisualFixture -SufficiencyFixture
```

真实视觉联合验收必须显式指定连接，并且只允许 2 次视觉模型调用：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File benchmarks/run_zotero_native_fixture.ps1 `
  -Target output/zotero/native-glm-visual-<new-name> `
  -VisualFixture -VisualLive `
  -ModelConnection <connection-id>
```

### 6.4 配对消融复跑

先使用人工核对过的 `development` 或 `test` 数据集；不要把合成 smoke 当作科研结果：

```powershell
python benchmarks/evaluate_knowledge_qa.py \
  --root <root> \
  --dataset <dataset.json> \
  --output <report.json> \
  --expected-split test \
  --strategies adaptive \
  --algorithm hybrid_rerank \
  --sufficiency-gates off on \
  --with-model
```

这个命令固定同一问题、知识库范围、revision、算法和策略，只改变门禁开关。报告会分别记录完成率、错误回答、调用数、已知/未知用量和延迟。当前没有真实人工 gold，因此不能从合成或脚本替身报告宣称提升。

## 8. 下一步：先做评测，不继续堆基础设施

下一步不是再增加 Agent 或模型，而是用真实 Zotero 文献建立小规模人工核对集：

1. 从真实问答历史导出原文问题候选；
2. 人工核对 PDF 页码、逐字引文、是否应该拒答；
3. 固定 development/test split；
4. 对同一问题运行门禁 off/on 配对实验；
5. 分别统计支持正确率、错误回答、错误拒答、完成率和调用成本；
6. 只有在 test 集上完成人工复核后，才讨论是否值得默认开启。

这一步才能回答门禁最重要的实际问题：它是否真的减少无依据回答，还是只是让系统更保守。
